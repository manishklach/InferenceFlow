# InferenceFlow v0.3.0 — Sub-hour scheduling (review candidate)

This review candidate adds an opt-in scheduling foundation for testing a 60-minute best-effort completion objective. It is not a public deployment, GPU benchmark, formal SLA or verified cost advantage. No paid GPU, live payment or external account is needed for the included local tests and simulation.

## Added

- DeadlineEstimator with token work, compatible backlog, current warm slots, conservative uncertainty, observed-throughput fallback and explicit calibration provenance.
- Configurable 3,600-second v2 target, persisted best-effort admission predictions, and strict `reject_if_at_risk` HTTP 503 before reservation when confidence/capacity is insufficient.
- Bounded deadline urgency and age bonuses atop existing weighted served counters, tenant caps, model affinity and wallet/lease safety.
- Independent adaptive-dispatch flag with hard limits, fresh telemetry requirements, additive increase, multiplicative decrease, hysteresis/cooldown and conservative missing/stale fallback.
- Recommendation-only CapacityPlanner: startup/load overhead, backlog risk, GPU-count/daily-spend/session ceilings, upward-rounded billing increments and idle-stop advice. No provider execution path.
- Migration 0006 for admission snapshots, first-dispatch timestamps, adaptive state, per-attempt observations, GPU activity samples and internal cost profiles.
- Internal quoted versus provider-invoiced costs, coverage/reference reconciliation, separate token volumes, attributable revenue, CPM and estimated gross margin. No customer price or wallet changes.
- Tenant-scoped performance API/SDK/dashboard and a separately authenticated operator capacity/economics view. Prometheus scheduling metrics and stale-data filtering.
- Six deterministic offline scenarios comparing baseline, deadline and adaptive policies, with raw JSON and an honest tradeoff report.
- Editable Mermaid architecture source, scheduling/economics/product/testing guides, and the founder-oriented blog post.

## Compatibility, rollout and rollback

Both `SCHEDULER_V2_ENABLED` and `ADAPTIVE_DISPATCH_ENABLED` default false. Existing explicit targets, rates, idempotency, billing, tenant isolation, worker generations, fencing and retries remain. Default-policy v0.2 idempotency fingerprints are preserved. No custom token-level batcher replaces vLLM.

Back up PostgreSQL, stop old API/scheduler/worker processes, apply `alembic upgrade head` through 0006, then restart together. Enable new behavior locally first. To roll back scheduling behavior, disable both flags and restart services, leaving the additive observation schema and financial history intact. Old accepted jobs retain their target and persisted admission snapshot.

`PROVISIONING_ENABLED=false`, `STRIPE_ENABLED=false` and operator approval remain the safe integration posture. A published v0.3 release and merge require review; this document only prepares notes.

## Verification and limitations

Baseline: 56 Python tests passed, one opt-in real-GPU test skipped; Ruff/mypy passed. Final suite: 78 passed, one real-GPU test skipped; 31 existing platform regressions also pass with v2 enabled. Ruff/mypy and production dashboard builds pass. Exact simulation commands are recorded in `IMPLEMENTATION_STATUS.md` and `docs/performance/`. The dashboard production build includes tenant performance and the protected operator route.

Real NVIDIA/vLLM load, tokenizer/engine throughput, VRAM fit, actual provider costs, external Stripe/OIDC behavior and hour-long deadline reliability are unvalidated. Simulation assumptions cannot calibrate real admission. Some policy changes regress some synthetic metrics; see the comparison instead of inferring a universal improvement. Automatic provisioning, multi-model optimization, AMD and formal SLAs are deferred.
